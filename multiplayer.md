# Multiplayer (онлайн в реальном времени)

Сессионная игра на 2–4 человек. Игроки создают/входят в комнату по коду, играют
в общем мире, побеждает последний выживший (остальные уничтожены).

Транспорт — **socket.io**. Модель — **server-authoritative** (сервер = источник
правды): клиенты шлют намерения, сервер валидирует и применяет, рассылает
состояние. Всё состояние сессий живёт **в памяти процесса Node** (без БД).

Реализация ведётся поэтапно. **Phase 1 (сделано) — вся сетевая инфраструктура и
лобби, запускается и тестируется end-to-end.** Phase 2 — перенос самой симуляции
на сервер (план ниже).

---

## TL;DR — как запустить

```bash
npm install
npm start                 # http://localhost:3000
```

Открой две вкладки браузера:

1. Вкладка A → «Create game» → появится код комнаты (4 символа).
2. Вкладка B → введи код → «Join». Игроки видят друг друга в списке в реальном времени.
3. Оба жмут «Ready», хост жмёт «Start» → у каждого запускается игра с назначенным
   сервером цветом/замком.

Тесты инфраструктуры:

```bash
npm test                  # tests/lobby-flow.test.js — поднимает сервер сам
```

Состояние сервера: `GET /health` → `{ rooms, sockets, uptimeSec }`.

## Ответы на инфраструктурные вопросы

**Всё хранится в памяти?** Да. Каждая сессия — JS-объект (`Room`) в `Map` внутри
процесса. БД не нужна для live-матча: состояние существует только во время партии,
после финала комната удаляется из памяти. БД может понадобиться позже и отдельно
(аккаунты, история партий) — не для MVP.

**Можно ли одним процессом Node обслуживать много сессий?** Да, это штатный режим.
Node однопоточный, но event loop держит много независимых комнат; у socket.io есть
встроенные **rooms** (`io.to(roomId).emit(...)`) — каждая комната изолирована, со
своим состоянием и своим серверным циклом (`setInterval`, а не `requestAnimationFrame`).

**«Нельзя, чтобы падал процесс Node».** Полностью исключить нельзя, но сделано три
уровня защиты, чтобы падения были редкими и не катастрофичными:

1. **Изоляция тика комнаты** — каждый серверный тик обёрнут в `try/catch`
   (`server/rooms/room.js`, метод `#tick`). Баг в логике одной партии не роняет
   ни другие комнаты, ни процесс. После `MAX_TICK_ERRORS` подряд ломается **только
   эта** комната (`status='broken'`), остальные живут.
2. **Глобальные предохранители** — `process.on('uncaughtException' | 'unhandledRejection')`
   в `server/app.js`: логируем, процесс не убиваем.
3. **Process manager (рекомендация для прода)** — PM2 / systemd / Docker
   `restart: always` как fallback при действительно фатальном крахе. Активные
   матчи при этом теряются (in-memory) — для пет-проекта приемлемо. Снапшоты на
   диск/Redis для восстановления — опционально, Phase 3.

## Карта файлов

### Сервер (`server/`)
| Файл | Назначение |
| --- | --- |
| `app.js` | express + http + socket.io, глобальные предохранители, `/health` |
| `config.js` | порт (env `PORT`), частота тика, лимиты игроков, длина кода, TTL пустой комнаты |
| `constants/slots.js` | слоты игроков (цвет, стартовый замок); `userId` совпадает с клиентом |
| `net/protocol.js` | имена событий socket.io (контракт C2S / S2C / INTENT) |
| `net/handlers.js` | подписка на события сокета, маршрутизация в Room/RoomManager |
| `rooms/room-manager.js` | реестр всех сессий: создание, поиск по коду, привязка сокетов, очистка |
| `rooms/room.js` | одна сессия: игроки, слоты, лобби→игра→финал, изолированный тик, победа |
| `game/simulation.js` | headless-симуляция партии (Phase 1 — скелет, Phase 2 — полная логика) |

### Клиент (`client/`)
| Файл | Назначение |
| --- | --- |
| `net/protocol.js` | зеркало серверного протокола (держать синхронно) |
| `net/network.js` | обёртка socket.io-клиента: запросы с ack + подписки |
| `ui/lobby.js` | экран лобби: коннект, создание/вход, живой список, ready/start |
| `main.js` | бутстрап: сначала лобби → по `game:start` запускает игру с назначенным слотом |
| `index.html` / `index.css` | разметка и стили лобби + оверлей финала; `<script>` socket.io |

### Изменения в существующем коде (минимальные)
- `client/game/game.js` — конструктор принимает `localPlayer` (раньше был жёстко
  `PLAYER_PROFILES[0]`). Идентичность теперь приходит от сервера.
- `client/constants/players.js` — добавлен 4-й слот `green-player` (для 4 игроков).

### Тесты (`tests/`)
- `lobby-flow.test.js` — e2e: create / join по коду / ready / start / назначение
  слотов / intent в бою / победа последнего выжившего. Сам поднимает сервер на
  отдельном порту. `npm test`.

## Протокол (socket.io события)

Источник правды — `server/net/protocol.js` (+ зеркало на клиенте). События с `→ ack`
отвечают колбэком.

### Клиент → Сервер
| Событие | Payload | Ответ (ack) |
| --- | --- | --- |
| `room:create` | `{ name }` | `{ ok, roomId, code, you, room }` |
| `room:join` | `{ code, name }` | `{ ok, you, room, error? }` |
| `room:leave` | `{}` | `{ ok }` |
| `lobby:ready` | `{ ready }` | — |
| `lobby:start` | `{}` (только хост) | `{ ok, error? }` |
| `intent` | `{ type, payload }` | `{ ok, error? }` (Phase 2: игровые действия) |

### Сервер → Клиент
| Событие | Payload | Когда |
| --- | --- | --- |
| `room:state` | полное состояние комнаты/лобби | при любом изменении (вход/выход/ready) |
| `game:start` | `{ you, players, world, seed }` | хост стартовал партию |
| `game:snapshot` | снимок мира (Phase 2) | каждый N-й тик во время игры |
| `game:event` | адресные события (тост/ресурсы — Phase 2) | по ходу игры конкретному игроку |
| `game:over` | `{ winner: { slot, name } \| null }` | остался один живой игрок |
| `net:error` | `{ message }` | ошибка |

### Типы `intent` (объявлены, обрабатываются в Phase 2)
`placeBuilding` · `trainKnight` · `moveOrder` · `shopExchange` · `upgradeArmy` · `harvestFarm`

## Жизненный цикл сессии и условие победы

```
lobby ──(host: start, все ready, ≥2 игрока)──▶ playing ──(остался 1 живой)──▶ over
                                                  │
                                                  └─(MAX_TICK_ERRORS подряд)─▶ broken
```

- **Слоты/идентичность.** Сервер назначает слот при входе (первый свободный):
  цвет, заголовок, стартовый замок. Слот 0 = хост. `userId` слотов совпадают с
  `client/constants/players.js`, поэтому клиентский рендер цветов/команд работает.
- **Готовность и старт.** `canStart` = лобби + ≥ `MIN_PLAYERS` + все `ready`.
  Стартует только хост.
- **Выбывание.** В бою выход/дисконнект игрока = его выбывание (`alive=false`).
  Phase 2 добавит выбывание по разрушению замка/всех зданий (сервер положит слот в
  `pendingEliminations`, `Room` его обработает).
- **Победа.** Когда живых ≤ 1 — `game:over` с победителем; цикл комнаты
  останавливается.
- **Очистка.** Пустая комната удаляется из памяти через `EMPTY_ROOM_TTL_MS`.

## Phase 2 — перенос симуляции на сервер (план)

Сейчас после старта каждый клиент крутит **свою локальную** симуляцию (как раньше),
сервер лишь назначил идентичность. Чтобы мир стал общим и авторитетным, симуляция
переезжает в `server/game/simulation.js`. Хорошая новость: код уже хорошо разделён,
переиспользование высокое.

### Что переезжает почти как есть
- **`KnightSystem`** (`client/game/knights/knight-system.js`). Методы симуляции
  (`update(dt, state, W, H)`, `spawn`, `issueOrder`, `selectUnitsInWorldRect`,
  `countKnightsForOwner`, …) уже принимают простые аргументы. Методы рендера
  (`render`, `renderLocalPlayerTrianglesOnTop`) на сервере просто **не вызываются**.
- **`StateManager`** (`client/engine/state/`) — чистая структура клеток, без браузера.
- **Экономика/стройка/фермы** из `client/game/game.js` — выносятся в чистый модуль
  без обращений к `ui`/`controls`/`renderer`.
- `performance.now()` — глобал в Node 16+, таймеры построек переедут без правок.

### Три шва, которые надо развязать
1. **Ввод: `Controls` → intents.** Сейчас `Game.update()` тянет ввод из `Controls`
   (`consumeRightClickWorld`, `getClickedCoords`, `consumeMarqueeSelectionWorldRect`).
   На сервере источник — `applyIntent(slot, intent)`. Клиентские обработчики мыши
   шлют `network.sendIntent(...)` вместо локальных мутаций.
2. **Вывод: `UI`-колбэки → события.** В `game.js` разбросаны `this.ui.showToast`,
   `setResources`, `openMarketShop`, `openKnightUpgrade` и т.п. На сервере это
   заменяется на адресные `game:event` нужному игроку (или убирается из ядра
   симуляции).
3. **Мир без вьюпорта.** `#setupWorld` сейчас зависит от размера канваса
   (`renderer.getRendererSize()`) для генерации деревьев по краям. На сервере мир
   фиксированный 64×64 — генерим только игровое поле, одинаковое для всех. Сид
   мира уже есть (`room.seed`) — генерацию деревьев надо сделать детерминированной
   от сида, чтобы у всех был один лес.

### Синхронизация состояния (клиент-зеркало)
- Сервер каждый N-й тик шлёт `game:snapshot`: сериализованные клетки `state`
  (x, y, spriteType, ownerUserId, hp) + рыцари (**нужны стабильные id**: x, y, hp,
  owner, facing, walk-флаг) + ресурсы/апгрейды по слотам.
- Клиент перестаёт симулировать: его `StateManager` и `KnightSystem` становятся
  **тупыми зеркалами**, наполняемыми из снапшота. Рендер при этом почти не меняется
  (`canvas-renderer.drawState` и `KnightSystem.render` уже принимают состояние/юнитов).
- **Выделение юнитов остаётся на клиенте** (своё у каждого игрока), привязано к id
  рыцарей из снапшота.
- Для плавности при тике сервера 20 Гц — интерполяция позиций рыцарей на клиенте
  (или слать чаще). Можно начать без интерполяции и добавить, если рвано.

### Производительность при многих комнатах
В `game.js` несколько мест сканируют **весь** `state` каждый тик
(`#enforceStorageCapsAllPlayers`, `#countBlacksmithsForPlayer`, `#maxKnightsForPlayer`,
`#maxStoredWheatWoodForPlayer`). На одной игре в браузере это ок, но при N комнатах в
одном процессе полные обходы суммируются и подъедают event loop у всех сразу (нет
вытеснения — тяжёлый тик одной комнаты тормозит другие). При переносе эти счётчики
стоит сделать инкрементальными (обновлять при постройке/разрушении, а не пересчитывать).

## Phase 3 — за пределами одного процесса (когда понадобится)
- **Масштабирование на несколько процессов/машин.** WebSocket липкий к процессу →
  нужен **sticky sessions** на балансировщике + **`@socket.io/redis-adapter`** для
  межпроцессной синхронизации комнат. Для 2–4 игроков на сессию сейчас не требуется.
- **Реконнект.** Сейчас ключ игрока — `socketId` (при дисконнекте в бою — выбывание).
  Для переподключения нужен стабильный `playerId` (токен) + грейс-период вместо
  мгновенного выбывания.
- **Персистентность/восстановление матча** — периодический снапшот комнаты в
  Redis/на диск, чтобы пережить рестарт процесса.

## Известные ограничения Phase 1
- После старта мир **ещё не общий**: симуляция локальная у каждого (Phase 2 это
  закрывает). Лобби, presence, идентичность, условие победы по дисконнекту —
  работают по-настоящему.
- Реконнекта нет: выход в бою = выбывание.
- Один сокет = одна комната одновременно.
- Стартовые позиции 4 слотов заданы в `server/constants/slots.js` и
  `client/constants/players.js` — при желании подвинь для баланса.
