# Multiplayer (онлайн в реальном времени)

Сессионная игра на 2–4 человек. Игроки создают/входят в комнату по коду, играют
в **общем авторитетном мире**, побеждает последний выживший (у остальных разрушены
замки или они вышли).

Транспорт — **socket.io**. Модель — **server-authoritative**: сервер держит мир и
симуляцию, клиенты шлют намерения (intents) и рендерят снапшоты состояния. Всё
состояние сессий — **в памяти процесса Node** (без БД).

**Статус: Phase 1 + Phase 2 реализованы.** Сервер авторитетно гоняет всю симуляцию
(мир, экономика, рыцари, бой, победа); клиент — «зеркало», рендерит снапшоты и шлёт
намерения. Серверная логика и сетевой контракт покрыты тестами (`npm test`).
Остаётся ручная проверка рендера в браузере (две вкладки) и оптимизации (см. ниже).

---

## TL;DR — как запустить

```bash
npm install
npm start                 # http://localhost:3000
```

Две вкладки браузера:
1. Вкладка A → «Create game» → код комнаты (4 символа).
2. Вкладка B → ввести код → «Join» (видно друг друга в лобби в реальном времени).
3. Оба «Ready», хост «Start» → запускается **общий мир**: у каждого свой цвет/замок,
   действия одного видны другому.

Тесты (поднимают сервер сами, чистый Node):
```bash
npm test
# tests/world-sim.test.js        — симуляция: мир, замки, ресурсы, намерения, дельта
# tests/combat-elimination.test.js — бой: рыцари рушат замок → выбывание
# tests/snapshot-sync.test.js    — сетевой контракт: snapshot + отражение намерений
# tests/lobby-flow.test.js       — лобби: create/join/ready/start/слоты/победа
```

Состояние сервера: `GET /health` → `{ rooms, sockets, uptimeSec }`.

## Ответы на инфраструктурные вопросы

**Всё в памяти?** Да. Каждая сессия — объект `Room` (+ `WorldSim`) в `Map` процесса.
БД не нужна для live-матча; после финала комната удаляется из памяти.

**Один процесс Node — много сессий?** Да. socket.io rooms (`io.to(roomId)`) +
отдельный серверный цикл на комнату (`setInterval`, 20 Гц). Event loop держит много
независимых комнат.

**«Процесс не должен падать».** Три уровня защиты:
1. **Изоляция тика комнаты** — каждый серверный тик в `try/catch`
   (`server/rooms/room.js#tick`). Баг одной партии не валит другие/процесс; после
   `MAX_TICK_ERRORS` ломается только эта комната (`status='broken'`).
2. **Глобальные предохранители** — `uncaughtException`/`unhandledRejection` в
   `server/app.js`.
3. **Process manager (прод)** — PM2/systemd/Docker `restart: always` как fallback.

## Архитектура Phase 2

```
КЛИЕНТ (браузер)                         СЕРВЕР (Node, ESM)
 Controls (ввод) ──┐                      Room (сессия, цикл 20Гц, try/catch)
 UI/модалки  ──────┼─ intents ──socket──▶  Simulation ─▶ WorldSim (авторитетно)
 Game(networked):  │                          ├ StateManager (карта)
   #handleNetworkedInput                      ├ KnightSystem (юниты/бой)
 Game.render ◀── snapshot ──socket──────────  └ экономика/стройка/фермы
   #applySnapshot → StateManager(зеркало)   collectSnapshot(): cells (дельта/кейфрейм)
                  → KnightSystem(зеркало)                    + knights + players
```

- **Сервер — единственный источник правды.** Клиент не симулирует: `Game` в сетевом
  режиме (`networked`) не крутит локальную логику — только применяет снапшоты и шлёт
  намерения. Локальный одиночный режим сохранён (Game без `network`).
- **Переиспользование кода.** `WorldSim` импортирует «листовые» модули клиента как
  есть: `StateManager`, `KnightSystem` (уже multiplayer-aware — все методы берут
  `ownerUserId`), `TreesGenerator`, `forest-regrowth`, экономику, константы. Вся
  симуляция — один код, исполняется и в Node (сервер), и в браузере (одиночный режим).
- **ESM везде.** `package.json` → `"type": "module"`; сервер и тесты переведены на
  `import/export`, чтобы напрямую импортировать клиентские ESM-модули.

### Поток данных
- **Ввод → намерения.** Клик/постройка/найм/приказ/магазин/апгрейд переводятся в
  `network.sendIntent(type, payload)`; сервер валидирует (переиспользуя ту же
  геометрию/экономику) и применяет. Ошибка валидации возвращается в ack → тост.
- **Снапшот → рендер.** Сервер шлёт `game:snapshot` каждый 2-й тик (~10 Гц):
  - `cells` — только renderable-клетки и только при изменении карты (по версии) +
    **кейфрейм раз в ~2с** (страховка от пропуска). Клиент восстанавливает отпечатки
    зданий через `tiles[spriteType]`.
  - `knights` — компактные тапл-объекты (id, owner, x, y, hp, mode, faceLeft) каждый снапшот.
  - `players` — ресурсы/апгрейды/лимиты/жив по каждому слоту.
- **Выделение юнитов — на клиенте** (своё у каждого), по id из снапшота; move-намерение
  несёт выбранные `knightIds`, сервер применяет приказ к ним.

## Протокол (socket.io)

Источник правды — `server/net/protocol.js` (+ зеркало на клиенте).

### Клиент → Сервер
| Событие | Payload | Ответ (ack) |
| --- | --- | --- |
| `room:create` | `{ name }` | `{ ok, roomId, code, you, room }` |
| `room:join` | `{ code, name }` | `{ ok, you, room, error? }` |
| `room:leave` | `{}` | `{ ok }` |
| `lobby:ready` | `{ ready }` | — |
| `lobby:start` | `{}` (хост) | `{ ok, error? }` |
| `intent` | `{ type, payload }` | `{ ok, error? }` |

`intent.type`: `placeBuilding` `{toolKey,tx,ty}` · `trainKnight` `{worldPx,worldPy}` ·
`moveOrder` `{wx,wy,knightIds}` · `shopExchange` `{kind,qty}` · `upgradeArmy` `{kind}` ·
`harvestFarm` `{tx,ty}`.

### Сервер → Клиент
| Событие | Payload | Когда |
| --- | --- | --- |
| `room:state` | состояние лобби/комнаты | изменение лобби |
| `game:start` | `{ you, players, world, seed }` | старт партии |
| `game:snapshot` | `{ tick, v, cells?, knights, players }` | каждый 2-й тик в игре |
| `game:over` | `{ winner: {slot,name}\|null }` | остался один живой |
| `net:error` | `{ message }` | ошибка |

## Что осталось (Phase 2.x / Phase 3)

**Phase 2 — сделано в полировке:**
- **Интерполяция рыцарей** — клиент сглаживает позиции между снапшотами (lerp к
  серверной цели каждый кадр, снап при больших скачках). `KnightSystem.interpolate`.
- **Анимация удара у зеркальных юнитов** — кадры рубки крутятся по `mode` (на сервере
  цель боя, у клиента её нет), `animMs` идёт в `interpolate`.
- **Живые полоски HP** — снапшот несёт точечные HP-дельты повреждённых клеток
  (`snap.hp`), пока полная карта не пересылается; полоски рубки меняются в реальном
  времени, а не «full → вдруг исчез».

**Phase 2 — ещё отполировать:**
- **Ручной тест в браузере** (две вкладки) — рендер/ввод покрыты headless-смоук-тестом
  (`client-render-smoke`) и сетевым контрактом, но не реальным браузером.
- **Дельта карты (terrain)**: `cells` всё ещё шлёт все renderable-клетки при изменении
  карты (во время рубки леса — часто). Перейти на точечные дельты добавлено/убрано,
  особенно для леса (~тысячи клеток). HP уже дельтится; геометрия — нет.
- **Адресные события** `game:event` (тосты/модалки конкретному игроку) — сейчас ошибки
  намерений приходят в ack, но серверные события (например авто-сбор) не пушатся.
- **Инкрементальные счётчики** вместо полных обходов `state` в подсчётах (кузницы,
  лимиты, склады) — при многих комнатах в одном процессе.
- **Темп рубки** (`CHOP_HIT_INTERVAL_MS=550`, урон 15, замок 200 HP) — это баланс,
  не баг; крутить при желании.

**Phase 3 — за пределами одного процесса:**
- Несколько процессов/машин: sticky sessions + `@socket.io/redis-adapter`.
- Реконнект: стабильный `playerId` (токен) + грейс-период вместо мгновенного выбывания.
- Персистентность/восстановление матча (снапшот в Redis/на диск).

## Заметки по балансу/исправлениям
- **Фикс рубки многоклеточных зданий.** Рыцари «замирали» в ~3px перед зданиями 2×2
  (например замок): подход целился в центр клетки стоянки, а порог касания —
  `CHOP_TOUCH_GAP_PX=1`. Теперь подход прижимает рыцаря вплотную к грани отпечатка
  (`#chopApproachPixelGoalTopLeft`). Это чинит и одиночный режим (рыцари не могли
  разрушать большие вражеские здания).
- Стартовые позиции 4 слотов — в `server/constants/slots.js` и
  `client/constants/players.js` (держать синхронно), при желании подвинуть для баланса.
